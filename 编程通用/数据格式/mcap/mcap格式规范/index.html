MCAP格式规范

MCAP这数据格式高大上点说可以描述为：面向时序消息流、支持多模态数据、自描述、可索引、可回放的数据容器。 但是实际上完全不用这么理解，把它当一个更高级的结构化日志就好:

黑话 翻译
面向时序消息流 存的消息带时间戳
支持多模态数据 可以存图，存json，存文本，因为本质上它只是存了二进制数据+数据格式描述，面向对象一点的描述就是它存了type+object
自描述 格式自带说明
可索引 消息带键，某种哈希表，某种字典
可回放 日志本身就是当时的数据，可以用来反复调试

核心抽象

这文件格式的抽象里最核心的四个：

  • Header：这个文件遵循什么约定。
  • Schema：消息的数据结构是什么。
  • Channel：消息属于哪个数据流。
  • Message：某一次实际产生的数据。 这四个抽象的关系如图： 下面以Go的MCAP库为例分别讲解

Header

type Header struct {
    Profile string
    Library string
}

这就是所谓的自描述的一部分了，其中

  • profile声明这文件中编码的格式遵循哪一套额外的规定，比如Profile:"ros2"
  • library记录生成这个文件的库或者程序的信息，记录生产者，方便调试和追溯

schema := &mcap.Schema{
    ID:       1,
    Name:     "sim.LidarEvent",
    Encoding: "jsonschema",
    Data: []byte(`{
        "type": "object",
        "properties": {
            "type": {"type": "string"},
            "scan_id": {"type": "string"},
            "sequence": {"type": "integer"},
            "sample_time_ms": {"type": "integer"},
            "total_points": {"type": "integer"},
            "total_packets": {"type": "integer"}
        }
    }`),
}

你就可以写这么个schema来描述这个json的结构，每个字段分别是什么数据类型，这样十万八千年之后有人刨出来这个文件，所有文档和上下文都丢失了，还可以在这里根据指定的格式把数据从二进制来序列化出来。

type Channel struct {
    ID              uint16
    SchemaID        uint16
    Topic           string
    MessageEncoding string
    Metadata        map[string]string
}

本质上是对数据源的抽象，注意其中的Topic字段，虽然常用于记录MQTT的Topic，但是实际上这字段只是用于区分数据源的字段，完全可以记录UDP，串口……等等数据源，随你怎么写

check(writer.WriteChannel(&mcap.Channel{
    ID:              1,
    SchemaID:        1,
    Topic:           "sim/lidar/events",
    MessageEncoding: "json",
    Metadata: map[string]string{
        "source":    "lidar-simulator",
        "transport": "mqtt",
        "frame_id":  "lidar_link",
    },
}))

注意这里为什么会附带一个类型信息MessageEncoding,在MCAP的设计里直接将数据类型与数据源绑定，而Message实际上是MCAP存储数据的最小抽象，其中存储的是纯二进制，因此它里面不存在任何的编码格式的信息。另外Metadata里存储的是数据源的描述信息

Message 

1
2

type Message struct {
    ChannelID   uint16
    Sequence    uint32
    LogTime     uint64
    PublishTime uint64
    Data        []byte
}

Sequence这设计一眼就是为了记录元数据的顺序了，基本上采用一个这样的规则：

  • 元数据自带序列号就用元数据序列号
    • 这样后续排查的时候就能看到1，3，5，4，2这种情况
  • 元数据不带序列号则接收端自己生成序列号
    • 这样虽然生成出来看起来数据是1，2，3，4，5，但是在对具体数据的时候可以对出来序列号和实际包的序列不对应的情况，虽然麻烦，但是依旧可以记录异常
  • 完全不在乎顺序就直接赋0，这没啥好说的

LogTime与PublishTime这俩字段倒是值得说一下，其中LogTime自然就是接收时间，注意一下从接收到写入的延迟，不要赋上写入时间就好，而PublishTime则一般用包自带的时间戳，如果没有自带的那就只能用LogTime将就了，不过另外这里有个比较值得注意的情况：如果数据源实际上用的是采样时间，而不是发布时间，但是可能它内部从采样到发布过了十万八千年，这里就会有个比较烦人的误记 Data自然没什么好说的，就纯原数据的二进制，MCAP这文件格式的设计目的核心就是这里，原始数据与派生数据应当区分，尽可能避免不可逆的数据处理，但是与此同时要记录尽可能多的信息，以方便回溯
