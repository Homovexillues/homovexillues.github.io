断点与调试

创建 2026-09-21 修改 2026-09-21 字数 约 900 字  阅读 预计阅读 2 分钟

从入行起就开始用IDE的程序员可能会问出这样的一个问题:"话说在IDE出现之前，人们是怎么打断点的？"

  • 编译型语言断点依赖的是操作系统底层的调试API
    • Unix是ptrace
    • Windows是Debug API
  • 而解释型语言/脚本语言，调试依赖解释器内置钩子，不是CPU内置陷阱指令
  • 内核调试会更麻烦：用户态ptrace不能调试内核，要用kgdb，或者硬件调试器(JTAG)
  • 调试符号
    • 调试符号记录了行号、变量名——>对应机器码地址。
    • 如C#这种，在编译程序的时候会生成一个.pdb文件，即调试符号文件
  • 软件断点
    • 调试器直接修改目标进程内存：把断点位置的CPU指令替换成一条陷阱指令（x86是int3,0xCC),CPU执行到这里的时候触发异常，操作系统暂停进程，把控制权交还给调试器，调试器此时把指令换回原来的代码，就可以看到寄存器，内存，单步
    • 可以直接用调试器来单步调试，比如最著名的GNU的gdb，就是个交互式的纯终端调试器

# 编译时带上调试信息 -g,调试符号直接附加在可执行文件上，不带这个参数就默认不附加
>>> gcc -g test.c -o test 
>>> gdb ./test 
# 在main第20行打断点
>>> (gdb) b main:20  
>>> (gdb) run 
# next单步 
>>> (gdb) n 
# print变量x 
>>> (gdb) p x
# 打印调用栈 
>>> (gdb) bt
