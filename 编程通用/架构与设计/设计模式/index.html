设计模式的分类

总体来说设计模式分为三大类：

创建型模式，共五种：工厂方法模式、抽象工厂模式、单例模式、建造者模式、原型模式。

结构型模式，共七种：适配器模式、装饰器模式、代理模式、外观模式、桥接模式、组合模式、享元模式。

行为型模式，共十一种：策略模式、模板方法模式、观察者模式、迭代子模式、责任链模式、命令模式、备忘录模式、状态模式、访问者模式、中介者模式、解释器模式。

这三种设计模式分别关注:如何创建对象,如何组织类与对象,如何在对象之间进行职责分配和交互。

经典的设计模式有23种。随着编程语言的演进，一些设计模式（比如Singleton）也随之过时，甚至成了反模式，一些则被内置在编程语言中（比如Iterator），另外还有一些新的模式诞生（比如Monostate）。

  • 创建型

常用的有：单例模式、工厂模式（工厂方法和抽象工厂）、建造者模式。

不常用的有：原型模式。

  • 结构型

常用的有：代理模式、桥接模式、装饰者模式、适配器模式。

不常用的有：门面模式、组合模式、享元模式。

  • 行为型

常用的有：观察者模式、模板模式、策略模式、职责链模式、迭代器模式、状态模式。

不常用的有：访问者模式、备忘录模式、命令模式、解释器模式、中介模式。

        switch (type)
        {
            case "A":

        }
    }
}

//我们以“日志记录器（Logger）”为例，实现两种不同的日志输出方式：Console 日志与 File 日志
public interface ILogger
{
    void Log(string message);
}
public class ConsoleLogger : ILogger
{
    public void Log(string message)
    {
        Console.WriteLine($"[Console Logger] {message}");
    }
}

public class FileLogger : ILogger
{
    public void Log(string message)
    {
        // 简化实现，实际要考虑IO处理、文件路径等
        File.WriteAllText(@"",$"{message}");
    }
}
//定义抽象工厂
public abstract class LoggerCreator
{
    // 工厂方法
    public abstract ILogger FactoryMethod();

    // 提供公共逻辑，这里演示一个示例
    public void WriteLog(string message)
    {
        // 通过工厂方法获得具体日志类
        ILogger logger = FactoryMethod();
        // 写入日志
        logger.Log(message);
    }
}
//定义具体工厂
public class ConsoleLoggerCreator : LoggerCreator
{
    public override ILogger FactoryMethod()
    {
        return new ConsoleLogger();
    }
}

public class FileLoggerCreator : LoggerCreator
{
    public override ILogger FactoryMethod()
    {
        return new FileLogger();
    }
}

public interface IPrototype
{
    IPrototype Clone();
}
//这其中包含一个Clone()方法，所有实现该接口的类都必须提供克隆自身的逻辑
//浅拷贝
public class ConcretePrototype : IPrototype
{
    public string Name { get; set; }
    public List<string> Tags { get; set; }

    // 浅拷贝：直接使用 MemberwiseClone()
    public IPrototype Clone()
    {
        return this.MemberwiseClone() as IPrototype;
    }

    public override string ToString()
    {
        return $"ConcretePrototype [Name={Name}, Tags={string.Join(",", Tags)}]";
    }
}
//深拷贝
public class DeepPrototype : IPrototype
{
    public string Name { get; set; }
    public List<string> Tags { get; set; }

    // 深拷贝：自己动手复制复杂引用类型的内容
    public IPrototype Clone()
    {
        // 先浅拷贝
        DeepPrototype copy = this.MemberwiseClone() as DeepPrototype;

        // 对引用类型字段进行单独拷贝
        copy.Tags = new List<string>(this.Tags);

        return copy;
    }

    public override string ToString()
    {
        return $"DeepPrototype [Name={Name}, Tags={string.Join(",", Tags)}]";
    }
}

//产品类
public class Computer
{
    public string CPU { get; set; }
    public int Memory { get; set; }
    public int Storage { get; set; }
    public string GPU { get; set; }

    public override string ToString()
    {
        return $"Computer: CPU={CPU}, Memory={Memory}GB, Storage={Storage}GB, GPU={GPU}";
    }
}
//抽象建造者
public interface IComputerBuilder
{
    //定义了建造步骤
    void BuildCPU();
    void BuildMemory();
    void BuildStorage();
    void BuildGPU();
    
    //最后返回最终构造好的产品对象
    Computer GetComputer();
}
//具体建造者
public class GamingComputerBuilder : IComputerBuilder
{
    private Computer _computer = new Computer();

    public void BuildCPU()
    {
        _computer.CPU = "Intel Core i9";
    }

    public void BuildMemory()
    {
        _computer.Memory = 32; // 32 GB
    }

    public void BuildStorage()
    {
        _computer.Storage = 2000; // 2 TB
    }

    public void BuildGPU()
    {
        _computer.GPU = "NVIDIA GeForce RTX 4090";
    }

    public Computer GetComputer()
    {
        return _computer;
    }
}
//办公电脑建造者
public class OfficeComputerBuilder : IComputerBuilder
{
    private Computer _computer = new Computer();

    public void BuildCPU()
    {
        _computer.CPU = "Intel Core i5";
    }

    public void BuildMemory()
    {
        _computer.Memory = 16; // 16 GB
    }

    public void BuildStorage()
    {
        _computer.Storage = 512; // 512 GB
    }

    public void BuildGPU()
    {
        _computer.GPU = "Integrated Graphics";
    }

    public Computer GetComputer()
    {
        return _computer;
    }
}
//指挥者
public class ComputerDirector
{
    public void Construct(IComputerBuilder builder)
    {
        builder.BuildCPU();
        builder.BuildMemory();
        builder.BuildStorage();
        builder.BuildGPU();
    }
}
//电脑指挥者里只有一个构建方法，它知道构建流程，依次调用CPU、内存、存储、GPU 的建造。
//在更复杂的场景里，你也可以在指挥者里灵活地对建造步骤进行顺序/配置上的调整。
//有时也可以不使用 Director，而是让客户端自己一步步调用建造者的方法——这取决于你是否需要一个统一封装的“指挥过程”。

设计模式的优缺点

优点

  1. 封装复杂构造：将复杂对象的创建过程分步骤封装到建造者里面，客户端不必关注各个零件如何装配。
  2. 更易扩展：需要变更或增加产品的组成，可以新建一个 ConcreteBuilder 或调整指挥者的构建流程。
  3. 符合单一职责：Builder 只负责如何一步步创建对象，Director 负责指挥建造流程，Product 对象则只是数据结构。

缺点

  1. 类数量增加：对于每种产品变体，都需要一个对应的 ConcreteBuilder。
  2. 不适合变化过于频繁的场景：如果对象结构本身经常变动，Builder 也要不断调整。
何时考虑使用建造者模式
  • 需要创建的对象内部结构复杂，且存在多种组合或变体。
  • 需要将复杂的构造过程与对象本身的业务逻辑分离，使得构造过程可以被单独管理或扩展。
  • 希望通过不同的建造者来创建“同一类对象”的不同版本（如游戏版、办公版、低配版、高配版等）。

//接口定义
public interface ISubject
{
    void Request();
}
//真实对象
public class RealSubject : ISubject
{
    //在没有代理的场景下，客户端会直接调用它的Request()
    public void Request()
    {
        Console.WriteLine("RealSubject: 处理请求的具体逻辑...");
    }
}
//代理对象
public class ProxySubject : ISubject
{
    private RealSubject _realSubject;
    private bool _userHasPermission = false; // 模拟权限

    public Proxy(bool userHasPermission)
    {
        _userHasPermission = userHasPermission;
    }
    public void Request()
    {
        // 在这里可以加一些 "调用前" 的额外操作
        Console.WriteLine("Proxy: 检查/预处理/延迟实例化...");
		if (!_userHasPermission)
        {
            Console.WriteLine("Proxy: 用户没有权限，拒绝访问");
            return;
        }
        // 延迟实例化(懒加载)：只有真正需要时才创建 RealSubject
        if (_realSubject == null)
        {
            _realSubject = new RealSubject();
        }

        // 调用真实对象的方法
        _realSubject.Request();

        // 在这里可以加一些 "调用后" 的额外操作
        Console.WriteLine("Proxy: 记录日志/缓存结果/后处理...");
    }
}

常见用途
  1. 虚拟代理（Virtual Proxy）：
  • 当对象的实例化非常昂贵（如远程图片加载、大型数据），代理可以在使用前不去初始化对象，只有当需要访问时才进行创建，来节省资源。
  1. 远程代理（Remote Proxy）：
  • 用于隐藏一个对象实际在远程系统中（比如分布式架构、远程服务器）。客户端只调用代理，就像调用本地对象一样，代理会通过网络把请求转给远程对象。
  1. 保护代理（Protection Proxy）：
  • 用于控制对真实对象的访问。可以在代理层做权限验证、角色检查等。
  1. 缓存代理（Cache Proxy）：
  • 针对一些需要重复查询的结果，代理可以先去缓存里找，如果命中则直接返回，提高性能。
优缺点

优点

  1. 在不修改真实对象的情况下扩展功能：对外仍然是同样的接口，灵活性高；
  2. 增强或限制对目标对象的访问：如权限校验、懒加载、缓存等；
  3. 分担职责：把一些通用逻辑（缓存、日志、权限等）从真实对象抽离到代理，简化真实对象的实现。

缺点

  1. 增加类数量与系统复杂度：每个真实对象都需要对应的代理类；
  2. 调用速度可能变慢：由于多了一层间接调用。
  3. 过度使用 也会让系统难以维护，需谨慎设计。

//目标接口
public interface INewLogger
{
    void WriteLog(string message);
}

//被适配的类
// 旧系统的日志类
public class OldLogger
{
    // 假设旧的日志方法是这样
    public void LogMessage(string msg)
    {
        Console.WriteLine("OldLogger: " + msg);
    }
}
//适配器
public class LoggerAdapter : INewLogger
{
    private OldLogger _oldLogger;

    public LoggerAdapter(OldLogger oldLogger)
    {
        _oldLogger = oldLogger;
    }

    public void WriteLog(string message)
    {
        // 在这里进行适配
        // 也可以进行其他转换，比如在旧方法前后加些逻辑
        _oldLogger.LogMessage(message);
    }
}

class Program

常见用途

对象适配 vs. 类适配

  • 上面展示的方式是一种对象适配（通过持有被适配者的实例）。
  • 另外还有“类适配器”，在 C# 里通常借助继承 + 接口实现，但因为 C# 不支持多继承，类适配器用得并不多。对象适配更常见。

何时使用

  • 当你想要复用一些已有的类/接口，但它们的接口形式与新需求不兼容时。
  • 又或者你不能修改现有类（可能是第三方库或遗留系统），就用适配器给它包一层，让它变成可用的接口形式。
优缺点

优点

  • 复用已有功能：不用重写或复制粘贴代码。
  • 对原对象无侵入：不必修改 Adaptee 源码，只需在适配器中做转换。
  • 耦合度低：新系统的模块依然只依赖 Target 接口，而非硬编码到 Adaptee。

缺点

  • 增加一层间接调用（性能影响一般不大，但存在）。
  • 如果接口差异较大，适配器需要编写的转换逻辑可能更复杂。
