C里的array decay会不会涉及到堆上的内存分配？

挺傻的问题，其实肯定是不会的，不然这机制设计得也太傻逼了，问题是为啥不会？原理是什么？

C有个广为人知的特性是int *可以被视为int arr[],因为本质上都是内存上一块连续的内存，但是很明显这俩所处的位置是不一样的：int arr[10]是在栈上的，而int *p = malloc(10 * sizeof(int))则是在堆上分配的(另外值得一提的是sizeof(p)永远是指针大小，而sizeof(arr)则是整个数组的总字节)。而在传参的时候，如果你定义一个这样的函数:void func(int p[]),那么你传递arr进去的时候它会默认衰减成指针，编译器会翻译成void func(int *p),这就是所谓的array decay。

不过其实答案挺简单的，arr传递了&arr[0]的地址。不过这里脏的地方就来了——free(),由于这指针指向的地址是个栈上的地址，你是不能free()它的,敢释放直接给你抛未定义行为，而你在没有LSP的情况下也只能靠眼睛去一点点的查，然后祈祷你足够细心，或者足够遵守编程规范，哪里分配哪里释放……

顺便这里描述一下free(p)之后它会做的事：

当你malloc一块内存的时候，分配器会在你拿到返回地址的前面存一块元数据

1
2

[ header 元数据 ｜ 你能用的内存区域 ]
                ↑ 你拿到的 void* p

而free(p)之后，分配器会拿到p的地址往前倒推，找到这个header，然后拿去校验，看它是否合法，是自己管理分配的堆块。所以如果你传过来的这个指针的地址：是栈地址/全局变量地址/mmap出来的，不是这个分配器分配的/已经free过的野指针，那自然找header就只能找到一堆随机的垃圾，然后各种libc就会各显神通，干嘛的都有，开始进入随机死亡模式

所有的可以让你自己摆弄内存的语言里的释放原语都差不多是这个思路——分配器在堆块前埋头，释放的时候找头去校验
