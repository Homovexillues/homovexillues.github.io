Docker容器和虚拟机的区别是啥？

一个docker的container为**[程序，环境]，而环境又是[操作系统，用户配置]** 而操作系统又分为了**[用户空间，内核空间]，应用程序运行在用户空间**，而作为一个容器，它不真的像是虚拟机一样需要操作系统内核空间的部分，只需要阉割掉内核空间，只保留用户空间，就能构建出程序运行所需的环境。

打比方就像是小别墅和居民楼，一个小别墅有自己的水电煤气这些基建，这就是虚拟机，而公寓则是共享整个楼里的水电煤气等基建，自己没有单独的基建。

dockerfile就是写好了从系统开始到运行我所需的程序所需要的所有操作，定义了环境，创建文件夹，等等

镜像就像是一个自带运行环境的程序安装包，而容器则是这个安装包启动的进程实例，即：

  • 镜像为只读模板
  • 容器为镜像+临时可写层+主进程

为啥运行容器不能默认用Root？

这就接了上面的问题，因为Docker维护的是容器而不是虚拟机，它是共享系统内核的，所以都不用提如果镜像本身有什么远程控制漏洞之类的问题，就最基本的，容器访问宿主机文件的时候是靠直接挂载在宿主机上实现的，一旦挂载语句写错了，写了个类似-v /:/host之类的语句，这个程序就直接拥有root权限然后可以在你的根目录下想干嘛就干嘛

所以其实编译的时候用个root问题不大，因为你编译的行为也不会进入最终运行的环境，但是最后运行时用root就比较危险了

什么是多阶段构建？

比如一个Go的程序，普通构建可能把编译环境和运行环境打包在一起，但是实际上对于编译型的语言，可以不用带编译器，程序运行实际上只需要二进制文件和一些所需信息啥的，而多阶段构建则是使用多个FROM一起搭建的：

1
2
3
4
5
6
7
8
9

# 第一阶段 编译
FROM golang:1.26 as builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /out/butler .
# 第二阶段 运行
FROM alpine
COPY --from=builder /out/butler /usr/local/bin/butler
CMD ["butler","serve"]

这样第一阶段的builder负责生成butler二进制文件，而第二阶段只从他那里拿最终产物，这样就能打出一个更小，更安全的镜像出来

什么是镜像层和构建缓存？

docker中的涉及环境和文件的命令基本上都会产生一个镜像层,在构建的时候Docker对每条指令会算一个缓存键，这个键包含三样：

  • 指令本身，如RUN go mod download
  • 父层的ID
  • 这条指令的输入，比如COPY会输入文件内容的哈希，RUN会输入父层的内容

而一旦在构建的时候发现上一层变了，后几层的镜像都会随之被放弃重新申请，所以语句的顺序就很重要，可能会出现这种情况：

1
2
3
4
5
6
7
8
9

# 错误示范
COPY . . # 复制项目
RUN go mod download # 下载依赖
RUN go build -o butler .
# 正确示范
COPY go.mod go.sum ./ # 只复制依赖清单
RUN go mod downlaod # 下载依赖
COPY . . # 复制源码
RUN go build -o butler .

上面的错误示范里，如果项目里的任意代码文件修改了，再打包镜像就会直接报废之后的下载依赖步骤，要重新下载依赖

而下面的正确示范里，由于是后复制文件，那么上面的下载依赖的镜像层得以保留，就不用重新下载了，在打包大的项目的时候这个顺序还挺重要的来着

另外这里还有个经典的坑：

执行apt update的时候，由于实际上变更了网络的内容，但是由于指令文本完全一致，它可能会给你一个缓存了的过期包列表，所以构建的时候要记得加--no-cache

为啥不把程序依赖的服务比如数据库，反向代理啥的都打包进一个镜像里？

技术上是可以跑在一个容器里啦，但是实际上不应该这么做，这样塞到一起的话就会出现这么个情况：

  • 一个服务要升级，整个镜像得重建
  • 进程崩溃的时候错误信息难以定义，比如你镜像里塞了3个进程，然后其中一个挂了，这错误状态debug起来就享受到了(
  • 无法分别扩容，其实也是第一条的问题，这里的所有服务，任意一个你需要改动，你就得把整个镜像给干掉

什么是build context?

就构建上下文嘛，字面义，不过这里需要解释的其实主要不是这个，而是Docker的运行模式，安装了之后Docker会先开起来一个Docker daemon,即后台的服务，这个服务主要用来维护正在运行的镜像等等，而执行Dockerfile的时候，其实就是把这些上下文文件发给这个Docker daemon，然后由它来打包，而我们用的docker命令，实际上是docker的client，docker是个经典的C/S架构的软件

而为了防止在把构建上下文里掺入一些敏感文件一并发给Docker daemon来打包成镜像，就需要写**.dockerignore**文件来排除一些比如.git文件，含有个人信息的配置文件等。

为啥配置和密钥不能放进镜像里？

这里就涉及到之前的镜像层知识点了，首先你都打包成镜像了，你一定要假设这东西是公开的，隐私信息一定不能掺进去，其次是关于之前的分层结构，Dockerfile执行的时候每一层都会分一个层，哪怕你在父层导入了配置，然后在下一层就删除了配置，这个配置的缓存还是在的，完全有可能会被恢复。

另外ARG和ENV也不行，ARG的语句可能会进入构建历史，而ENV会直接将数据保存在镜像元数据和容器环境中。

docker run xxx:latest 这个:latest是啥？

镜像引用，完整格式为[仓库地址/]镜像名[:标签]，比如：

docker build -t butler:latest 构建的时候打的标签就是“latest”，而默认标签就是latest，不指定标签直接写docker run xxx的时候跑的就是latest版

dockerfile有个ENTRYPOINT，也有个CMD，这俩有区别吗？

这就和上面的那条有关了，比如写了这么个配置:

1

CMD ["butler","serve"]

那运行docker run butler（这里的butler是镜像名）的时候确实是能跑，但是如果这么写:

docker run butler tree,在没有EntryPoint的情况下它会默认把tree当成参数，整体替换调CMD，然后找不到tree命令，报错

所以一般情况下，都是用ENTRYPOINT指定默认运行哪个程序，用CMD指定默认给这个程序什么参数，也就是这样：

1
2

ENTRYPOINT ["butler"]
CMD ["serve"]

这样再执行docker run butler:latest tree的时候，执行的就是butler tree了，而不是直接报错，当然docker其实也提供了参数可以让你绕过默认的ENTRYPOINTdocker run --entrypoint /bin/sh butler:dev

再就是为啥推荐写成JSON数组形式而不是CMD butler serve类似的写法呢？因为这种写法就会被识别成shell form,即理解成/bin/sh -c "butler serve",所以最好写成“exec form”,即那种JSON数组的格式

Docker里的PID 1是啥？

容器启动后有个主进程，通常PID是1，容器关闭的时候，会先向这个PID 1发送一个SIGTERM,等一段时间，如果还没退出，则发送SIGKILL

即如果程序不处理SIGTERM,则Docker会到超时后强制杀死它

为啥数据不能只写进容器文件系统

容器运行时会在镜像上增加一个临时可写层，向/app/state.json写入内容时，就是在写这一层容器可写层

同一个容器停止再启动，文件通常还在，但是如果删除容器再用镜像开起来，则原容器的可写层就消失了，因此需要持久化的数据就要写到：

  • bind mount

    docker run -v /home/homovexillues/config:/app/config butler

    即将宿主机上的指定目录挂载到容器里的指定地址

  • Docker volume

    1
2

    docker volume create butler-data
docker run -v butler-data:/app/data butler

    Docker托管的仓库，即Docker管理的卷，实际在/var/lib/docker/volumes/butler-data/下

    这就是Dockerfile里VOLUME关键字的用法,不过这个关键字有个问题，即它只是声明地址必须为挂载点，但是你如果启动容器的时候没有显式的声明挂载，那么它就会自动创建一个名称为随机64位哈希的名字来当卷，像这样：

    1
2
3
4
5

    homovexillues@xxxxxxxx ~> docker volume ls
DRIVER    VOLUME NAME
local     961dffacaceb4b80ad3990519e57aeeb8ceb73ff937abace7710c302b29327a8
local     n8n_data
local     plane-app_logs_api
